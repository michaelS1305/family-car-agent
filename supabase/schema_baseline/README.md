# FCA current production schema baseline

**DO NOT APPLY TO THE EXISTING FCA PRODUCTION DATABASE.**

This is a CURRENT production-schema reference / empty-database bootstrap baseline,
not a chronological migration, upgrade, repair, or production execution task.
Existing production already reached this state through legacy manual creation
and later manual migrations. `../manual_migrations/` remains the historical
rollout/change record. In particular, `2026090601_family_roles_expand.sql`
execution history remains UNKNOWN.

## Files and scope

- `current_schema.sql`: one transactional, guarded snapshot of FCA-owned objects.
- `validate_capture.py`: read-only local comparisons against the supplied Markdown
  captures; no database connection, SQL execution, or generated files.

Source: all ten operator-supplied files in `../schema_audit/`. Those temporary
evidence files are neither rewritten nor copied into this baseline. The complete
Join-session section supersedes the overlapping original truncated section;
identical overlapping columns are deduplicated, not silently changed.
Migration/application code is provenance only, not the schema authority.

## Safety and prerequisites

The SQL intentionally refuses execution unless a future operator explicitly sets
the session setting `fca.allow_empty_baseline` to `yes` on an approved empty
bootstrap/disposable database. This is an accident guard, not proof that a database
is non-production. Never opt in on the existing production database.
It additionally requires postgres and absent FCA tables/functions. Existing
sequences, indexes or policy conflicts fail transactionally; there is no
IF NOT EXISTS reconciliation or replacement of an existing FCA schema.

For a future separately authorized bootstrap, Supabase must already supply
`auth.users`, `auth.uid()`, `realtime.messages`, `realtime.send()`,
`realtime.topic()`, the public/auth/realtime schemas, and the postgres, anon,
authenticated and service_role roles. Its Realtime table security/runtime must
already be configured. This baseline does not create Supabase internals.
The local search_path resolves captured unqualified FK/sequence/function
references to public; function-local empty search_path definitions remain exact.
Do not replay historical migrations over this current-state snapshot.

## FCA Realtime customizations

Both exact captured function definitions are included:

- public.broadcast_car_status_changed(): SECURITY DEFINER, volatile,
  empty search_path; only postgres/service_role EXECUTE.
- public.can_receive_car_status_topic(text): SECURITY DEFINER, STABLE,
  empty search_path; anon/authenticated/postgres/service_role EXECUTE.

PUBLIC has no EXECUTE, per the earlier operator-confirmed live audit.
The AFTER INSERT car_events_broadcast_car_status trigger and PERMISSIVE
authenticated SELECT policy family_members_receive_car_status on
realtime.messages preserve the captured definitions/qualifier. No INSERT policy
is introduced. Provider table ownership, policies other than this FCA policy,
partitions and publication membership are not changed.

## Security representation

The complete supplied table privilege results show seven table privileges
(DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE) for postgres
(grantable) and service_role (not grantable), on every FCA table.
New-object browser/PUBLIC/service_role defaults are revoked before explicit grants
are restored, within the same transaction. No explicit column ACLs were captured,
and none are introduced. Sequence SELECT/UPDATE/USAGE are granted to
postgres/service_role without grant option; owner authority remains intrinsic.
Browser/PUBLIC sequence access stays absent.

The function capture reports effective EXECUTE for named roles rather than full
ACL grantor/grant-option tuples. SQL preserves the confirmed role access and
ownership; exact historical ACL provenance is not claimed. Similarly, table
privileges are captured through grantability results, not original grantor tuples.

Schema privileges are environment prerequisites, not FCA-owned alterations:
public USAGE is true for anon/authenticated/postgres/service_role; CREATE is true
only for postgres among those four roles. This baseline does not modify shared
schema ACLs or infer ACLs for unobserved roles.

## Data boundaries

Only two approved bootstrap configuration rows are inserted:
gemini-default = 50 and google-geocoding = 20. updated_at uses the captured
column defaults, not live values. No users, families, history, codes, Auth users,
reservations, conversations, sessions, attempts, permits, subscriptions,
confirmations or deletion jobs are copied. family_code_history starts empty
for a fresh bootstrap; this is not a recovery/export of historical code values.

## Live-versus-repository differences and limitations

- Live RLS is enabled on seven tables above, including six newer tables whose
  creation migrations do not enable it; Join setup also omits its live RLS flag.
  The live state wins.
- Live car_events has a family FK, whereas init_db's IF NOT EXISTS column pattern
  cannot reliably establish that FK.
- Chat tables, conversation request FK/partial indexes and actual users column
  order are taken from captures rather than the incomplete legacy setup DDL.
- Creator NOT NULL is preserved; this does not establish 0601 execution history.
- Physical dropped-column slots, sequence runtime counters, historical grantors
  and uncaptured function grant-option tuples are not reproduced.
- This artifact has static capture comparisons only; no SQL was executed during
  preparation. A future bootstrap execution needs separate authorization and
  validation against a disposable Supabase-compatible environment.

Run `python supabase/schema_baseline/validate_capture.py` while the operator
