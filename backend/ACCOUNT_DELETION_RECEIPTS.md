# Durable deletion confirmation and local cleanup

## Contract

`GET /api/account/deletion/capabilities` returns
`{"protocol":"deletion-status-v1","retention_days":180}` only when
`DELETION_RECEIPTS_ENABLED=true`. Otherwise 503. Responses are no-store.

New clients MUST use `POST /api/account/deletion/request`, with a valid Bearer JWT:

```json
{"confirmation":"DELETE_MY_ACCOUNT","status_credential":{"operation_id":"<canonical UUID v4>","secret":"<43-character unpadded base64url encoding of 32 CSPRNG bytes>"}}
```

The client stores owner, environment, operation and secret durably BEFORE sending.
The dedicated new route is intentional: a capability check followed by a legacy
POST is unsafe behind mixed-version servers. Old servers cannot handle this route.
There is no automatic legacy fallback. The optional credential is also understood
by the existing POST; existing clients with no credential retain their old contract.

202 response: `{"operation_id":"...","status":"pending"}`. Exact authenticated
initiation retries return the same association. Changed secret/owner/operation is
rejected; existing legacy jobs are never adopted. After job finalization clients
retrieve the result through the credential route, not an expired JWT POST.

`POST /api/account/deletion/status`, empty body, header
`Authorization: DeletionStatus <operation_id>.<secret>` returns pending, or
`{"operation_id":"...","status":"completed","completed_at":"...","expires_at":"..."}`.
This endpoint is read-only and independent of JWT validity. Unknown, invalid and
expired credentials all return the same 401/no-store response. No 401 is evidence
of deletion. Database/service errors are not successful confirmations.

## Security and database

The server stores SHA-256(domain separator + operation UUID bytes + random secret),
not the secret. Comparisons use compare_digest, including dummy comparison on an
unknown operation. Credential validation is bounded and canonical. Initiation
bodies are limited to 1024 bytes and duplicate/unknown JSON keys are rejected;
validation never echoes the request body. Do not configure monitoring to capture
Authorization headers or deletion request bodies.

Deletion-scoped ASGI middleware applies no-store to routing, authentication,
validation, rate-limit and unexpected error responses. Unexpected errors return a
fixed private body without raw exception logging. Other APIs are unaffected.

Status uses a bounded, process-wide token bucket (30 burst, 5/second). This is not
a distributed ingress limiter: total capacity scales with worker count. Keep
existing ingress abuse controls. An attacker can exhaust this shared worker bucket;
per-client/distributed abuse controls remain for the security-hardening phase.
The capability authorizes no other endpoint.

Migration: `supabase/manual_migrations/2026112701_account_deletion_receipts.sql`.
The exact file was executed in fresh local PostgreSQL 17 databases after its actual
coordination/Apple predecessor migrations; no live database was accessed.
It is additive. RLS is enabled, anon/authenticated/public have no grants. Runtime
access uses the existing trusted DB connection; service_role receives only table
CRUD, no DDL. Confirm the actual Backend role's access during owner deployment.
Pending receipt references the active job, not auth.users. Completion clears the
job association and preserves only opaque operation/digest and timestamps.

Existing identity locks are acquired before operation locks. Job creation and
receipt creation share one transaction. Finalize writes the completed receipt
in the existing transaction before deleting the job. A trigger prevents OLD
workers from erasing a pending receipt's job. Their finalization rolls back and
can be resumed by an updated worker, even after Auth deletion.

Completed receipts expire after exactly 4320 elapsed hours (180 days). Reads never
extend retention. Pending receipts do not expire. The existing worker removes at
most 100 expired completed receipts per pass using SKIP LOCKED. No extra scheduler.

## Deployment and rollback

1. Owner reviews/applies the additive migration; it was executed only in disposable local databases.
2. Deploy updated API and ALL deletion workers with receipts disabled.
3. Verify grants, updated workers and protection against old-worker finalization.
4. Enable DELETION_RECEIPTS_ENABLED=true and verify capability AND request/status
   behavior using an authorized disposable test account.
5. Release updated iOS. Android can later implement this same protocol.

On rollback, disable new initiation but keep updated workers/status available for
pending receipts. An old worker cannot complete such jobs; never remove the guard
or infer completion to unblock them. Existing legacy clients/jobs remain legacy.

## iOS cleanup

Environment-specific, device-only Keychain item per owner. Secret generated by
SecRandomCopyBytes; no cloud synchronization. Durable completion replaces the
secret before cleanup. Repeated status reads recover a lost completion response.
Lost initiation may replay only the same saved operation with matching live auth.
A prepared credential is armed only after the existing deletion preflight succeeds;
a failed preflight never becomes an automatic deletion request on the next launch.
An explicit retry can resume that prepared operation.

A permanent SQLite v6 deleted-owner fence blocks recreation across processes.
Queue and registration/upload-file writes use the same SQLite exclusion lock.
Session Keychain writes are fenced as well; this deliberately fails closed if
local storage cannot validate the fence. Normal logout retains data and does not
create a deletion fence. Another account's active session is never cleared.

After durable completion, the owner is fenced and its exact background session
identifiers are recovered from SQLite and owner-scoped upload directories. The
client cancels those URLSession tasks and awaits session invalidation (15-second
bound) before cleanup. Timeout or an error-bearing invalidation callback preserves the completion record
for retry. A failed callback can never release cleanup; duplicate/late callbacks
cannot reverse a recorded result. Other
owners' sessions are not cancelled. Late callbacks cannot pass the persisted fence.

Files are removed before relational inventory under the lock. On file failure,
rows remain; on later SQL failure, the deleted account stays fenced and retry
removes remaining files/rows idempotently. Cleanup removes metadata, grants,
resolution attempts, events and device/sequence rows for the exact owner/environment.
The shared DB is retained. secure_delete and DELETE journal are enabled; VACUUM
removes freelist remnants. Parent directories are fsynced after file removal and
SQLite fullfsync is enabled. Busy/disk-full failures keep cleanup pending.

Push records are filtered by owner; stale registration results are fenced by the
existing epoch. Matching auth session is cleared under the cleanup lock. Cleanup
credentials are deleted only after every required operation succeeds. The minimal
SQLite owner/environment fence remains to reject stale writes.

No API can guarantee physical erasure from flash wear-leveling, OS snapshots or
backups already taken. Protected, backup-excluded application files and SQLite
logical cleanup/compaction are the guarantees here. Firebase's installation-scoped
SDK token is not an FCA account credential and is not reset.

## Diagnostics

Release OSLog prefix FCA_DEVICE_SETUP, subsystem com.familycaragent.device,
category setup. Fixed stage/reason enums and a bounded numeric category only
(0 unspecified, 1 missing, 2 denied, 3 disk full, 4 read only, 5 I/O).
Only allowlisted Cocoa/POSIX error codes map to these categories; domains and raw
numeric input are never printed. No arbitrary exception interpolation;
 no identifiers, paths, coordinates,
raw exceptions, credentials or payloads. Setup rejection distinguishes storage,
cancellation, epoch, generation, missing session, owner, activation, user, family.
Storage diagnostics distinguish directory resolution/creation, protection, backup,
SQLite open/init/schema, partition, journal read/decode and context mismatch.
SQLite prepare/bind/step errors emit their fixed reason and the primary SQLite
error code (1..28; unknown values map to 0). Central interception also covers
validateSequence query errors and static authorization persistence connections.
No SQL, bound values or sqlite3_errmsg is logged. The observer and Keychain fault
injection seams compile only in dedicated check binaries, never ordinary app builds.
The two authorizationStorageFailed origins are denyBindings and invalidation.
This is instrumentation, NOT a proven repair for the original setup incident.

## Limits and review gates

No automatic proof exists for historical deletions without a receipt. If both the
saved credential and local completion proof are lost, or the client returns after
receipt expiry, retain data and report uncertainty. Never infer from 401.

Physical Keychain failure, URLSession daemon cancellation, full Xcode app integration,
and physical-device foreground/restart behavior need CI/device verification.
Cross-SDK type-checking with composition stubs is NOT a full Xcode build.
The local test report must distinguish these from deterministic lifecycle/SQLite
and disposable PostgreSQL tests. No live database, signing, publication or deployment.
