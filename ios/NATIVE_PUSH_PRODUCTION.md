# Native Push: separate iOS Production project

Local implementation only. Nothing in this change activates Production, creates credentials,
applies migrations, uploads to Apple, or proves real device delivery.

## Trusted configuration

| Backend environment | Platform | Firebase project | App identity |
| --- | --- | --- | --- |
| dev | Android | family-car-agent-dev | il.fca.companion.dev |
| dev | iOS | family-car-agent-dev | com.familycaragent.app.dev; APNs sandbox |
| prod | Android | family-car-agent-dev | il.fca.companion |
| prod | iOS | family-car-agent | com.familycaragent.app; APNs production |

`family-car-agent-push` is a display name, **not** the project ID.
The server environment is pinned to the existing Supabase URL/package pair. The client
cannot supply a project, environment, bundle or credential override. Registration selects
the server-configured platform cohort; confirmation, refresh and authenticated revocation
select the cohort from the owned installation's stored platform/project. Unknown or mismatched
Production identities fail closed. An unknown owned installation is explicitly denied with the
existing registration-unavailable/access-denied response; no provider or fallback is selected.
The separate iOS capability endpoints use the server-selected iOS project and the existing
owner-bound cancellation secret. The capability can only cancel, never activate/read data.

FCM tokens are opaque: the server does not infer an app from token text. The existing
challenge/nonce protocol proves receipt via the selected Firebase project and APNs topic
before activation. This is not a new device-attestation mechanism.

The worker alternates isolated, bounded child passes for the two Production projects when
the iOS rollout flag is enabled. Each child reloads the same configuration as the API and
uses one project's credentials. No credential fallback or new retry path exists. The existing
20-second child deadline, leases, authorization checks, generation fencing and cleanup remain.
Reminder creation now enqueues all active installations of the recipient atomically with
the single event, just as vehicle events do; each project worker claims only its own deliveries.
This prevents the first project's unique reminder occurrence from excluding the other project.

## Render configuration to prepare later (API and worker)

Keep **all existing** `NATIVE_PUSH_*` Android/Dev settings and their secret file unchanged.
The existing base configuration is still required by the shared API/worker startup.
On Production only, prepare:

- `NATIVE_PUSH_IOS_PROD_ENABLED=true` only after separately approved activation; absent/false is off.
- `NATIVE_PUSH_IOS_PROD_PROJECT=family-car-agent`.
- `NATIVE_PUSH_IOS_PROD_CREDENTIALS_FILE`: absolute path to a separately mounted secret file.
- `NATIVE_PUSH_IOS_PROD_KEY_ID`: stable identifier for this encryption cohort.
- `NATIVE_PUSH_IOS_PROD_ENCRYPTION_KEY`: base64-encoded 32-byte encryption key.
- `NATIVE_PUSH_IOS_PROD_FINGERPRINT_KEY`: a distinct base64-encoded 32-byte HMAC key.

The service-account JSON must identify project `family-car-agent`, use the standard OAuth
token endpoint and have client email `fca-push-prod@family-car-agent.iam.gserviceaccount.com`.
It remains backend-only; never put it in a plist, app, source file, artifact or frontend secret.
No keys were generated by this task. Provision the cohort keys separately; retain them across
restarts. Existing key-cohort drift checks remain; rotation is not implemented by this change.
Missing/invalid configuration fails closed. Disabling the iOS flag also makes its server-side
revocation endpoints unavailable; the app retains pending cancellation for reconciliation.

Existing `NATIVE_PUSH_ENABLED` and `NATIVE_PUSH_REMINDERS_ENABLED` retain their meanings.
Do not change Android's project or credential file as part of this rollout.

## iOS and GitHub configuration to prepare later

Development remains the default, with its original Firebase plist, bundle, Debug build and
signing job. Production requires explicit `--production` wrapper/signing arguments and the
`FCA_PRODUCTION` Swift compilation condition. Release optimization alone never selects Prod.
The wrapper generates Production Info.plist and entitlements outside the source tree, with
the Production callback scheme and APNs environment. Runtime Firebase validation requires:

- bundle `com.familycaragent.app`;
- project `family-car-agent`;
- sender `249909620080`;
- app ID `1:249909620080:ios:12c8182ee0db3d93ee33b5`.

In the existing `ios.yml`, the new Production job requires manual dispatch on `develop`,
input `build_production_ipa=true`, and repository variable `FCA_PROD_SIGN_ENABLED=true`.
It uses GitHub environment `ios-production-signing`; configure required owner review there
before enabling it. No environment or repository settings were changed locally.

Required GitHub secrets (prefer the protected signing environment):

- `FCA_IOS_PROD_GOOGLE_SERVICE_INFO_BASE64`: the verified Production Firebase plist.
- `FCA_IOS_PROD_CERT_P12_BASE64`: existing Apple Distribution certificate/private-key export.
- `FCA_IOS_PROD_CERT_P12_PASSWORD`.
- `FCA_IOS_PROD_PROFILE_BASE64`: existing App Store Connect provisioning profile.

Required public build variable: `FCA_IOS_PROD_SUPABASE_PUBLISHABLE_KEY`, from the Production
Supabase project. Only a publishable key is accepted; no service-role key belongs in the app.
Its project association must be checked by the owner; the opaque key cannot prove that offline.
The generated auth callback is `com.familycaragent.app://auth/callback`; verify its existing
Production allowlist and native Google/Apple configuration before releasing.

The signer checks team `GT43M39TLK`, exact app identifier, unexpired iOS profile, no registered
device list or enterprise distribution, `get-task-allow=false`, APNs production and Apple sign-in.
It selects a certificate authorized by that profile, verifies signed entitlements and the packaged
app, and cleans its temporary keychain. Production profile names are not assumed.
The job produces an IPA artifact only: **no TestFlight/App Store upload or deployment**.
Actual Xcode compilation, codesigning and App Store acceptance require the macOS job later.

revocation identity already exist in the Native Push schema. Before activation, separately
verify that Production has the existing foundation, reminders and iOS revocation migrations
(`2026101801`, `2026101901`, `2026111201`). Live schema was not inspected or modified.

The offline runner disables dotenv loading, replaces the database pool and blocks database and
provider connections. Database integration suites are explicitly skipped without an isolated
local test database; mock checks are not a substitute for SQL concurrency tests. Initial direct
discovery attempted the existing pool's DNS lookup and was stopped after resolution failed;
subsequent runs used the isolated runner. No successful database connection or push send occurred.

After separate deployment approval: verify migrations/configuration, run the macOS signed build,
install through the approved distribution channel, and test a real iPhone's registration/refresh,
foreground/background notifications, vehicle and booking/maintenance reminders, logout, account
switch, offline cancellation/restart, deletion and denied notification permission. Recheck Android
Production and both Development clients. FCM acceptance is not proof of APNs/device delivery.
